## Cursor and reset rules to preserve

`PyEditor` already supports imperative `focus`, `goToLine`, `replaceAll` and `insert`. `replaceAll` dispatches a CodeMirror text transaction and sets the selection to text end; it does not explicitly focus. `insert` places a new line after the current line and focuses. Error-line decoration is mapped through edits and cleared on document change. These behaviors are source verified, not all necessarily desirable for every Reset action.

`Editor` for SQL keeps current Run/Check callbacks in a ref, memoizes extensions, uses schema-aware SQLite completion and wraps long lines. It does not expose a ref/transaction API. Avoid recreating the SQL editor merely to share the Python interface. If a reproduced reset problem requires a small handle, scope it to the affected caller and retain existing shortcut/completion semantics.

Acceptance for an eventual Reset repair: exact pre-reset text is recoverable once; the starter is unchanged; unrelated files are untouched unless explicit full-project reset was chosen; focus returns predictably; hint history and historical solves remain intact; no deferred controlled-value update overwrites newer typing. Verify cursor/selection separately from text persistence. File switching may recover saved text while still losing undo/caret state.

## Measured layout baseline and conditional repair specification

**Measured by the coordinating investigator:** no document overflow was observed at tested widths 1440, 768 and 390 pixels (`evidence/records/sql-layout-observations.json`). The desktop editor width was approximately 662px and the measured Python editor height was 180px. At 390px the Python lesson editor appeared around document y=2178 and SQL around y=1785 after prior activity; these are not pristine-load measurements or directly comparable content lengths. No pane separators were observed. A subsequent SQL project stage probe measured editor width/height at approximately 759×320px (1440 viewport), 389×320px (768), and 356×320px (390, document y≈1266), without overflow. Starter Run returned 20 rows, incorrect Check showed useful alias feedback, custom Run returned 44, and refresh retained stage query parameter and draft (`evidence/records/15-sql-project-actions.js.result.json`). Full project completion remains untested. These facts justify testing editor reachability and short-height comfort, not claiming desktop collapse or mobile horizontal overflow.

Record viewport, document width, pane/editor/action/result bounding boxes, scroll owners and caret visibility before/after Run. Use 1440×900, 1366×768, 1280×600, tablet portrait and 390px mobile as representative cases, not universal device guarantees. Zoom and a real mobile keyboard need separate observation; viewport emulation alone cannot validate keyboard occlusion.

- **Lesson:** preserve readable explanation and nearby runnable examples. On wide screens maintain an independently reachable work pane; on stacked layouts provide a clear route to the active exercise and back. Do not compress prose or hide requirements to create editor space.
- **Practice:** prioritize a useful code viewport while keeping task, schema and feedback reachable. An initial target of roughly eight visible code lines on a short desktop is a proposed usability criterion, not measured current failure. Keep horizontal table scrolling inside the result region.
- **Project:** preserve milestone identity, file context and written evidence. Reset scope and error-file navigation take priority over a file-tree redesign. Keep reference tabs and actions reachable with long file names and output.
- **Mobile:** use one clear page scroll where practical; nested editor/table scroll regions need visible boundaries and keyboard access. Keep action controls reachable when the keyboard is shown. Do not add a fixed bottom action bar until overlap with keyboard and safe-area insets is verified.

CSS edits, if approved later, should target the winning rules in `src/app/sql/rt.css` and `src/app/python/p2.css`; the SQL stylesheet contains successive overrides of editor heights and overflow. Inspect computed styles before removing “duplicates.” Do not refactor both stylesheets while repairing one measured geometry defect.
