# Engine quality: targeted investigation and repair plan

Source inspection: **2026-10-21**. SQL + Python only. This is an implementation proposal, not authorization to change code. No application tests, builds, generators or runtime probes were run by this engine auditor. Browser-confirmed findings are identified below and indexed in [REA_EVIDENCE.md](REA_EVIDENCE.md); other findings are **source-confirmed behavior** or explicitly **unverified risks**. Browser observations were supplied by the parent investigator, not executed by this source auditor. Preserve content, reference solutions, datasets, grading expectations and earned progress.

## Current baseline to preserve

- [`sql-client.ts`](../../../src/engine/sql-client.ts), `executeSql`: one global `pending` operation/worker, intentional latest-run-wins supersession; separate boot (12 seconds × up to three attempts), dataset (60 seconds), Run (3 seconds) and Check (8 seconds) budgets. `cancelSql` settles the caller even while booting. Do not replace this with an unbounded queue or worker pool.
- [`python/client.ts`](../../../src/engine/python/client.ts), `runPython`: one global active operation, fresh single-use interpreter each run, one global warm spare replaced for a changed package set; run ID/nonce filtering, streamed output, bounded stdout/stderr, typed results, stop and crash recovery. Core/package boot limits are 30/120 seconds; default execution is 5 seconds; mounted data cap is 64 MiB. Preparation is intentionally outside the code execution timer.
- SQL [`Cells.tsx`](../../../src/features/rt/Cells.tsx), `QueryCell`: already displays “edited since the last run”; `finally` clears busy even when superseded. SQL [`ProjectWorkspace.tsx`](../../../src/features/rt/projects/ProjectWorkspace.tsx), `run`: generation guards, query fingerprints and current evidence checks prevent edited queries receiving current verification. Preserve these mechanisms.
- Python [`CodePane.tsx`](../../../src/features/py/CodePane.tsx) already retains code alongside Run/Check results and passes `edited` to output renderers; [`PyRunCell.tsx`](../../../src/features/py/PyRunCell.tsx) already explains supersession. These are existing patterns, not functionality to invent. However current `/python/learn/[slug]`, `/python/practice/[slug]`, `/python/projects/[slug]` route files import `features/python` screens, which use [`Workbench.tsx`](../../../src/features/python/Workbench.tsx). Do not infer active-route parity from the older `features/py` components.
- Python's current factory uses [`createSandboxWorker`](../../../src/engine/python/sandbox.ts), an opaque-origin iframe/worker. The stale same-origin description in [`python-runner.ts`](../../../src/platform/python-runner.ts) does not describe that factory. Production remains disabled. This quality pass does not enable it.

## Confirmed SQL check-count feedback defect (E09 / P1)

**Browser-confirmed:** SQL practice `customer-list` passes Check but its check list says “Returns 200 rows” while expected/actual full results are 848. Evidence: [practice observations](evidence/records/practice-observations.json). This is misleading feedback, not evidence that the overall grader compared only 200 rows.

**Source provenance:** [`checks.ts::visibleChecks`](../../../src/features/rt/checks.ts) uses `expected.values.length` for its row-count label and compares `actual.values.length` with that preview length. [`engine.js`](../../../public/vendor/engine.js) performs full-result grading first, then slices both result and expected tables to 200 rows in its two response branches (lines 133–134 and 204–205 at inspection). It sends full actual `total` but no full expected count. [`Output.tsx`](../../../src/features/rt/Output.tsx) correctly uses `res.total` for its table summary.

**Further source risk, not separately reproduced:** actual and expected full counts may differ while both exceed 200, causing the row-count subcheck to appear passed even though the authoritative overall grade fails. Do not derive a count verdict from equal preview lengths.

**Proposed bounded repair:** carry full expected count (or a structured full-count check outcome) alongside the existing actual total from both worker response branches; update `ExecuteResponse` metadata and `visibleChecks` presentation. Preserve `compareResults`, all fixtures and authored expectations. Acceptance: matching 848/848 says 848; unequal counts above 200 do not produce a passing count check; empty/small/large results stay consistent with table summaries; preview remains capped and grading still sees full rows. Do not simply substitute actual total for expected total on failed checks.

## Recovery, output and correctness acceptance

These are future scenarios, not test results:

1. **Baseline loop:** valid Run → syntax error → corrected Run → wrong Check → corrected Check. Capture output, focus and button state at each terminal event. A program running successfully must not imply a passing grade.
2. **Stop and retry:** stop in runtime boot, dataset loading, Run and Check; immediately rerun. Verify exactly one terminal result per operation, no stale result replacement, no progress from incomplete work and usable next run.
3. **Worker failure:** a failed worker/package fetch produces an actionable preparation error; retry after recovery works. A run timeout is distinct from download/boot delay. Never auto-retry learner code invisibly.
4. **Rich output:** alternate stdout/stderr with table/figure output; inspect order and long traceback navigation. Current stdout cap is not a total figure/table/blob budget; stress findings should justify any additional limits. Do not truncate data before grading or alter expectation semantics. SQL worker currently compares full results before the 200-row presentation slice.
5. **Files:** edit main and helper, run, generate an artifact, switch files, rerun and refresh. Distinguish saved source, explicit learner files and ephemeral interpreter state. Keep fresh interpreter isolation; do not retain globals as a speed fix.
6. **Correctness freeze:** retain SQL original/changed fixtures, writes/state/plan/idempotence checks; retain Python typed comparisons, exceptions/mutation checks, probe/expected-value separation and all authored task expectations. No new simplified grader.

Existing regression intent to reuse after approval: [`tests/sql-client.test.ts`](../../../tests/sql-client.test.ts) covers timeout/crash/boot retry/cancellation and supersession; [`tests/python-client.test.ts`](../../../tests/python-client.test.ts) covers fresh workers, nonces, stop, recovery and mount hashing/preparation exclusion; [`tests/python-sandbox.test.ts`](../../../tests/python-sandbox.test.ts) covers relay/CSP structure. Their presence is not a fresh pass. Add only missing owner-race, cancelled-boot-late-retry, stalled-mount and active-workspace busy/stale scenarios. Appropriate real-browser coverage remains necessary.

## Measurement and launch boundary

Measure cold and warm **engine preparation**, **dataset preparation**, **execution**, **grading** and **rendering** separately on the same activity/package/fixture/device. Record cache condition, browser/device and successful/failed completion; do not label an automation wait or fixed capture delay as engine latency. Parent investigation recorded one observed foreground Run at approximately 80 ms after preload and a subsequent Check at approximately 6,035 ms, which includes fresh-runner/prewarm preparation. These are single automation-observed samples, not execution-only timings or a cold/warm benchmark. A reported SQL 42 ms sample matched expected-preview content rather than confirmed completion and is discarded; it is not a valid execution measurement. No new worker pooling, caching layers or package changes before measurements demonstrate a bottleneck.

Python production isolation is a separate required launch validation, not permission to enable deployment: actual deployed CSP/origin/egress/storage/message boundaries, cancellation/recovery and supported real devices must pass positive and adversarial scenarios. Existing local opaque-origin implementation and historical reports are credited, but no new production proof was obtained here. See [V2 isolation gate](../runtime-v2/06_EXECUTION_ENGINE_ARCHITECTURE.md) for the previously documented scope; this quality pass does not repeat or weaken it.

Recommended sequence: prioritize the confirmed E01 owner-control recovery, E09 SQL check-count feedback and E06 stale-feedback gaps; validate E02 and remaining ordinary edit/run/check variants; verify E03/E04/E05 under controlled delays; reconcile source risks with browser evidence; approve a small ownership/recovery patch; then improve proven stale/phase feedback gaps; measure performance before optimizing. A reproduced wrong-grade, source-loss or isolation failure overrides this order. No infrastructure redesign is proposed.
