## 1. Ids, order and the code changes they imply

How order works today (read from code):

- `registry.json` is generated by `scripts/pyspark/import-catalog.mjs` from the v4 CSVs. **Display order is array
  order**, not id order. `content.ts` numbers lessons and questions by array index (`number: i + 1`), and
  `validatePsRegistry` requires every lesson prerequisite to sit **earlier in the array** (`order.get(p) < order.get(id)`).
  Module order is the order of first appearance.
- So new ids can be **appended in id space and inserted in array space**. No ordering field is needed.

Required changes (small, all in the coordinator's lane):

1. **`import-catalog.mjs`**: leave the hashed v4 CSVs alone. Add an in-repo extension table (e.g.
   `scripts/pyspark/extensions.mjs`): modules with `after: "PS-M08"`, lessons with `after: "PS-L048"` (M16) or
   `after: "PS-L053"` (L097), question seeds (id, lesson, role, format, draft difficulty, optional tag). Merge it, emit
   questions grouped in lesson display order, and add `PREREQS` / `RELATED` / `REQUIRES` rows for L091–L097.
   `REQUIRES`: L091–L095 `sql`, L096 `plans`, L097 `arrow`. Extra questions on existing lessons (Q0486–Q0489, the
   classics) attach to those lessons' `questions` lists.
2. **`content.ts` `levelOf`** derives the level from the module *number* (`M16` → "advanced"). Change it to the
   module's display position (or add an explicit `level` to `PsModuleEntry`). Shown after M08, Spark SQL is
   "intermediate".
3. **`types.ts`**: optional `tags?: "classic"[]` on `PsQuestionEntry` (classics, §4). No new role.
4. **`tests/pyspark-registry.test.ts`** hard-codes 15 / 90 / 450 and "every module has 6 lessons". Update the counts
   and relax the module size to `>= 6` (M09 gets 7 with L097), and extend the "written" id lists.
5. **Practice page**: a "Classics" filter on `tags`. Nothing else in the UI keys on ids.

## 2. Engine facts and needed harness work (read from `services/spark-runner/`, nothing run)

- **Session**: `harness.py` builds a classic py4j session (`local[2]`, UTC, `spark.local.dir=/tmp/spark`, no Hive
  support), so the catalog is **in-memory**. ANSI is on by default. Delta's catalog is added only when the source
  contains the word "delta".
- **Warehouse**: the root fs is read-only, `/tmp` is the only writable place (512 MB noexec tmpfs), and the Dockerfile
  sets `WORKDIR /tmp` and `HOME=/tmp`. The default `spark.sql.warehouse.dir` is `spark-warehouse` relative to the
  working dir, so it resolves to **`/tmp/spark-warehouse`, which is writable**. `saveAsTable`, `CREATE TABLE … AS
  SELECT`, `CREATE DATABASE` should work within one job and vanish with the container **(verify)**. Noexec doesn't
  matter for Parquet (snappy's native lib is already in `/opt/native`).
- **Each lesson example is its own job.** `build_lesson` runs `playground()` once per example block, so a table made
  in example 2 doesn't exist in example 3. Catalog lessons must create what each example queries.
- **Grading cases share one session.** That's fine for temp views (`createOrReplaceTempView` inside `solve` refreshes
  them). It's unfair for tables: a correct `saveAsTable("t")` passes case 1 and then fails case 2 with
  `TABLE_OR_VIEW_ALREADY_EXISTS`, and a dropped catalog entry can leave a folder that raises
  `LOCATION_ALREADY_EXISTS` **(verify)**.

Proposed harness changes. They land in a new image (`4.0.1-4`), because `sandbox/` is copied into the image.

| # | Change | Size |
|---|---|---|
| H1 | Pin `spark.sql.warehouse.dir=/tmp/spark-warehouse` explicitly, so it doesn't depend on the working dir | 1 line |
| H2 | Before each case in `run_cases`: drop temp and global temp views, drop non-default databases (cascade) and default-db tables, `rm -rf /tmp/spark-warehouse` | ~15 lines |
| H3 | Optional job flag `"views": true`: register each input as a temp view named after its table before calling `solve`, so later SQL items can start with `def solve(transactions): return spark.sql("""…""")` | ~5 lines |
| H4 | Pandas API on Spark under ANSI. Spark 4.0's pandas-on-Spark is not fully ANSI-safe; it may refuse to run or need `ps.set_option("compute.fail_on_ansi_mode", False)` **(verify the exact option)**. Pick one: (a) a Delta-style switch that turns ANSI off only when the source imports `pyspark.pandas`, or (b) teach the option in L097 | ~5 lines |
| H5 | Spark Connect: **not available**. No grpcio / grpcio-status / googleapis-common-protos in the image, and `run_cases`/`plan_nodes` use `df._jdf`, which Connect DataFrames lack | see §3.4 |

**Grading SQL answers already works.** `load_solution` sets `module.spark`, inputs arrive as DataFrames, and `solve`
may register views and return `spark.sql(...)`. That result is a normal `DataFrame` and is graded as rows, the same
as any other answer. Practice items should accept any approach (authoring rule 4). Lesson **challenges** that teach
SQL can use the existing technique check with `"source": ["sql"]` (the AST check sees `spark.sql`; the SQL text
itself is a string and is never inspected).

Keep queries per job low (pids-limit 512, ~13 threads per query): at most ~15 `spark.sql` calls per example or item.
Never print `DESCRIBE EXTENDED` rows such as *Created Time* (they change per run); `Location` is stable only once H1 is in.

## 5. Difficulty calibration

**The problem.** Difficulty is the role: foundation=easy, business/debugging=medium, edge/integration=hard (450 items:
90/180/180). Many "edge" items are one concept plus one NULL rule, which is medium work.

**Rubric.** Four axes, 0–2 each, total 0–8 → **easy 0–2, medium 3–5, hard 6–8**.

| Axis | 0 | 1 | 2 |
|---|---|---|---|
| A. Concepts combined | the lesson's one concept | two concepts | three or more, or from different modules |
| B. Steps (transformations in the shortest correct reference) | ≤ 2 | 3–5 | ≥ 6 |
| C. Edge reasoning | answer unaffected by NULL/ties/duplicates/boundaries | one trap, named in the prompt or rules | an unnamed trap, or two that interact |
| D. Reference size (body lines) | ≤ 6 | 7–15 | > 15 |

Debugging modifier: −1 when the bug shows on the visible sample and needs a one-line fix.

**Process:**

1. A script scores B and D from `reference.py` (AST: chained calls and statements).
2. Authors record A and C in a private `calibration.json` per item.
3. The script sets the band. The registry test fails when `spec.difficulty` disagrees with the band.
4. Validate with a blind solver on ~40 items (a smaller model, cold, two attempts). Pass rates should order easy > medium > hard (aim ~85 / 60 / 35%).
5. Target mix per lesson: about 2 easy, 2 medium, 1 hard (~40/40/20 course-wide).
6. **Re-label, don't rewrite**: change the label, not the item. Labels don't affect progress.
